1. PROJECT OVERVIEW
============================================================

Project Name:
IBSBMS – Islami Bank Share & Bond Management System

Purpose:
IBSBMS is a web-based shareholder management system designed to
manage shareholder account information and control changes through
a Maker–Checker approval workflow.

The system supports:
- Viewing shareholder accounts
- Creating new shareholder records
- Modifying existing shareholder records
- Submitting changes for approval
- Checker approval, rejection, or return for modification
- Tracking request history
- Maintaining audit information

The system uses Spring Boot for the backend, Thymeleaf for the web
interface, and Oracle Database for persistent storage.

5. USER ROLES
============================================================

The application uses two main roles.

MAKER
-----
The Maker is responsible for entering and modifying shareholder
information.

Maker permissions include:
- View shareholder records
- Create shareholder records
- Modify shareholder records
- Submit requests for approval
- View own requests
- View requests returned for modification
- Resubmit returned requests

CHECKER
-------
The Checker is responsible for reviewing submitted requests.

Checker permissions include:
- View shareholder records
- View pending approvals
- Review request details
- Approve requests
- Reject requests
- Return requests to the Maker for modification
- View rejected requests
- View returned requests

7. CREATE SHAREHOLDER WORKFLOW
============================================================

A Maker does not directly create the final approved shareholder
record.

The workflow is:

Maker enters information
        |
        v
Server creates/reserves Folio/BO
        |
        v
Create change request
        |
        v
Approval request = PENDING_CHECKER
        |
        v
Checker reviews request
        |
        +-------------------+
        |                   |
        v                   v
     APPROVE              REJECT
        |                   |
        v                   v
Update master          Request ends
tables
        |
        v
Approved shareholder


The proposal is stored in T_SHAREHOLDER_CHANGE_REQUEST.

The approval state is stored in T_APPROVAL_REQUEST.

Actions such as Maker submission and Checker decisions are recorded
in T_APPROVAL_ACTION.

8. MODIFY SHAREHOLDER WORKFLOW
============================================================

For an existing approved shareholder, the Maker loads the approved
snapshot and edits the permitted fields.

The existing master data is not immediately overwritten.

Workflow:

Approved shareholder
        |
        v
Maker selects Edit
        |
        v
Load approved snapshot
        |
        v
Maker changes information
        |
        v
Create SHAREHOLDER_UPDATE request
        |
        v
Checker review
        |
   +----+---------+
   |              |
   v              v
Approve         Return/Reject
   |              |
   v              v
Update master   Request remains
tables          outside approval
   |
   v
Updated shareholder


The modification request keeps:

OLD_VALUE
---------
Snapshot of the previously approved data.

NEW_VALUE
---------
The Maker's proposed changes.


============================================================
9. RETURN FOR MODIFICATION
============================================================

A Checker can return a request when changes are required.

When a request is returned:

- Status becomes RETURNED_FOR_MODIFICATION
- Current stage becomes MAKER
- Checker information is retained
- Return remarks are recorded
- An approval action is created

The Maker can open the returned request and correct the data.

On resubmission:

- The same REQUEST_ID is retained
- The existing OLD_VALUE is preserved
- NEW_VALUE is replaced with the corrected proposal
- Version is incremented
- Status becomes PENDING_CHECKER
- Current stage becomes CHECKER
- Checker assignment is cleared
- A RESUBMITTED action is recorded

This allows the complete request lifecycle to be tracked.

17. IMPORTANT BUSINESS RULES
============================================================

1. A Maker submits changes; the Maker does not approve them.

2. A Checker reviews the Maker's request.

3. A Maker cannot act as the Checker for the same request.

4. Final master data should be updated only after approval.

5. Rejected requests are not applied to the master tables.

6. Returned requests can be corrected and resubmitted.

7. The original OLD_VALUE must remain available for modification
   requests.

8. Shares, Suspense, Bonus, and Balance are not Maker-editable
   business fields during shareholder modification.

9. Workflow history should remain traceable through approval actions.

10. Business date should be assigned by the server using the
    Bangladesh business timezone (Asia/Dhaka).

============================================================
21. CONCLUSION
============================================================

IBSBMS provides a structured shareholder management solution with
a controlled Maker–Checker workflow. The separation between
proposal data, approval state, action history, and final master
records provides traceability and helps prevent unauthorized direct
changes to shareholder information.

The application is designed using a layered Spring Boot architecture,
with role-based security and Oracle-backed persistence, making it
suitable as a foundation for further integration with production
banking systems and authentication mechanisms.
